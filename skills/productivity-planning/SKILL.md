# Productivity Planning Procedure

## Trigger / when to use
Load this skill when planning work, breaking down a project, setting goals, or running a daily/weekly review.

## 1. Write the outcome, not the activity
Define done as an observable state (`inbox at zero`, `draft sent to Ana`) with a date — never as effort (`work on email`). If done can't be observed, the goal is a wish; shrink it until it fits one verifiable sentence.

## 2. Break down to 30-minute steps
Decompose until every step fits one sitting. Steps that stay vague (`handle backend`) hide 5 sub-steps — split them. Record multi-step work with the `todo` tool and mark items done as you go; the shared list keeps parallel work honest and resumable.

## 3. Sequence by dependency, schedule by energy
Order steps so blocked work never starts first; put the hardest step in the first productive block of the day. Timebox each step (25–50 min) with a visible timer — open-ended steps expand to fill the day. One MIT (most important task) per day, chosen the night before.

## 4. Checkpoint the durable stuff
For multi-day efforts use goals with checkpoints (`mochi checkpoint save before-refactor`) so any step can be rolled back or resumed after interruption. End each day with a 5-minute review: what moved, what blocked, what is tomorrow's MIT. Unreviewed plans rot within 48 hours.

## 5. Pitfalls that kill plans
- Planning in more detail than the horizon allows — weekly plans stay coarse, daily plans stay exact.
- More than 3 active priorities — everything past 3 is a someday list wearing a costume.
- No definition of done per step — without it, 90%-done tasks pile up forever.
- Skipping the review when behind — the review is most valuable exactly when you want to skip it.

## 6. Verify the system weekly
Count completed vs planned steps, note repeat blockers, and retire or renegotiate anything carried over twice. A plan that never changes is a plan nobody reads — adjust scope openly instead of silently slipping.
